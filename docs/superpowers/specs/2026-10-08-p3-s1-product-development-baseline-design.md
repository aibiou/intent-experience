## 1. 产品判断

### 1.1 结论

本产品有值得验证的产品假设，核心技术路径可行，适合进入一个严格限界的首个切片；但当前没有用户行为、留存、支付意愿或分发数据，不能声称已经证明商业可行或产品市场匹配。

产品差异不应表述为“比通用聊天模型更聪明”，而应验证：

> 系统能否围绕用户当前意图运行一段可适应的体验，同时让用户始终能够纠正、改变方向、直接获得答案或停止。

### 1.2 可行性边界

- 工程上可行：用现有模型作为可替换能力提供者，产品状态、策略、验证和运行时由常规软件控制。
- 工程风险集中在状态单写入、异步取消、旧结果拒绝、上下文一致性、可追踪性与评测可信度，而非训练自有基础模型。
- 产品价值仍待验证：用户是否感知到“体验适应”优于普通问答、是否愿意主动回来，不能从架构或研究原型推断。
- 互动叙事研究已把用户主导权、分支探索和连贯性作为核心设计问题，但这只支持问题与技术路线值得研究，不证明本产品的市场需求。[ACL 2025：互动戏剧中的沉浸感与主导权](https://aclanthology.org/2025.acl-long.546/)；[Narrative Studio：分支探索与叙事连贯性](https://aclanthology.org/2025.wnu-1.16/)

### 1.3 当前阶段

- 产品定义与契约设计：已有较完整的候选文档。
- P2 证据关闭：归档中的 E8 登记为未通过，不能按已关闭处理。
- P3-S1：已有运行时垂直切片规范及原会话中的实现契约候选稿，尚未形成仓库内正式基线。
- 工程实现：仓库为空，尚无产品代码、测试执行证据或用户验证结果。

## 2. 不变产品原则

本文不修改以下既有原则：

1. 用户当前明确意图优先于历史记忆。
2. 用户可以随时停止；系统不得暗中续行。
3. 用户要求直接答案时，系统不得强迫其进入探索流程。
4. 大语言模型（LLM）只能提出候选结果，不拥有状态、策略或产品决策权。
5. 运行时（Runtime）是产品状态唯一写入者；非法、过期或未授权结果不得写入。
6. 记忆（Memory）提供上下文但不覆盖当前意图；用户主导权、状态完整性和策略边界属于硬阻断项。
7. 测试通过不等于产品正确；所有验收必须回溯到已批准的产品契约。
8. 跨集一致性是重要产品质量要求，但不得借此把 S1 扩大为完整创作平台。

## 3. P3-S1 范围

### 3.1 目标体验

以“探索型问题体验”（Exploratory Question Experience）作为首个切片的冻结候选。其目标是验证一个有限、可观测的体验运行链，而不是建设通用体验市场或内容信息流。

### 3.2 必须贯通的运行链

自然输入 → 用户意图（Intent）→ 体验状态（ExperienceState）→ 语义动作（Semantic Action）→ 策略（Policy）→ 大语言模型提案（LLM Proposal）→ 验证器（Validator）→ 状态机 / 运行时 → 状态变化 → 事件 / 决策轨迹 → 用户可见体验。

运行时是唯一状态写入者。前端、大语言模型、策略、验证器、记忆、数据分析、工具和模型供应商适配器均不能绕过运行时写入产品状态。

### 3.3 S1 验收核心子集

依 P3-S1 规范，核心子集至少验证：

- GS-01 直接回答（Direct Answer）：用户要求直接答案时直接回答。
- GS-02 原因解释（Why）：用户询问原因时给出解释。
- GS-03 改变方向（Change）：改变方向时，旧生成和旧候选失效。
- GS-04 停止（Stop）：停止后终止，不自动开启下一体验。
- GS-05 状态版本冲突（State Version Conflict）：拒绝过期状态写入。
- GS-06 拒绝模型改写状态（LLM State Mutation Rejection）：拒绝模型直接修改产品状态。

所有用例还需覆盖适用的边界、异常和恢复行为；P2 的 G01–G08 与 S1 的 GS-01–GS-06 必须建立逐项映射，不能因名称相似而视为同一套证据。

### 3.4 非目标与延期边界

S1 不建设社交、关注/点赞/评论、内容信息流/榜单、创作者市场、多智能体协作、强化学习排序、完整记忆中心、完整创作 IDE、长篇生成平台或自研基础模型。

S1 不实现完整 WHAT_IF 分支、搜索、创造分支和最小长期记忆；原规范将这些更完整能力放在后续阶段。是否有任何最小行为需要提前进入 S1，须先通过契约映射解决，不得由实现团队自行决定。

跨集创作一致性在 S1 只体现为状态、事实来源、上下文边界和决策轨迹的可验证约束；角色库、世界观编辑器、时间线管理和跨集创作工具不属于 S1。

## 4. P2→P3 门禁顺序调整提案

归档中的门禁存在闭环：G2–G4 要求真实实现的观察结果、代码版本和故障执行证据；E8 又规定 P3 实现必须等 P2 全部门禁通过。空仓库无法提供真实运行证据。

### 4.1 实现前：P3 准入门槛

在任何产品运行时代码开始前，必须完成：

1. G1：七份契约的唯一权威位置、版本、指纹、负责人和批准记录。
2. G2 静态阶段：CC-01 至 CC-12 均映射到明确契约条款；已知冲突已裁决或明确阻塞。
3. G6：PB-01 至 PB-04 均有明确处理结果；任何从阻塞项改为延期项的处理，必须由产品负责人批准并通过版本化治理修订，不得由实施团队自行解释。
4. G7：首个体验、标准路径及纳入 / 排除 / 延期范围已批准。
5. E5：真实证据执行环境、版本记录方案和独立评测角色已准备就绪。

此准入只授权实施已冻结的 S1，不代表任何运行时行为已通过验收。

### 4.2 实现后：P3-S1 证据门槛

在真实 S1 代码上执行动态跨契约验证、黄金验收子集、工程边界与故障测试、独立评测。P0 用户主导权 / 状态完整性 / 策略边界失败仍然阻断，不允许平均分抵消。

完整 G01–G08 中不属于 S1 范围的场景，必须明确映射到后续切片并保持未通过/未执行状态；不得伪报为 S1 已通过。

### 4.3 变更控制

以上仅是门禁顺序提案，不静默改写 E8，也不改变原有验收语义或降低标准。正式采用前必须将 P2 退出、P3 准入和 S1 退出的关系写成有版本号的治理修订，并完成负责人批准。

## 5. 产品开发阶段

### 阶段 0：建立权威基线

- 把归档与原会话中有效文档登记为仓库内的正式或候选文档，区分权威文件、候选文件、历史稿和重复件。
- 冻结七份契约的版本矩阵、跨契约权威关系和变更流程。
- 处理 P2 CLOSED 与 E8 BLOCKED 的状态冲突。
- 处理 C07–C08 与 C07–C09 的重叠，并确认正式 C4 大语言模型契约、E4 决策、E5 执行环境材料的权威位置。

### 阶段 1：实现准入

- 冻结探索型问题体验及标准路径。
- 冻结 S1 动作和案例范围，并建立 P2 G01–G08 到 S1 GS-01–GS-06 的映射。
- 冻结硬验收标准、统计指标与待定阈值；不擅自编造发布数字。
- 完成证据环境、独立评测和 AI 辅助编码团队执行协议。

### 阶段 2：运行时核心

实现顺序：

1. 核心数据结构、会话 / 用户意图 / 体验状态与版本控制。
2. 状态机与运行时单写入。
3. 语义动作与策略。
4. 大语言模型网关、调用/错误记录与验证器；模型输出不直接写状态。
5. STOP / CHANGE 取消、幂等、旧结果拒绝与决策轨迹。
6. 接口、事件、评测工具和最小用户界面闭合完整纵向链路。

技术栈与具体模块文件布局在仓库基线和技术决策记录阶段确定，不从空仓库臆造现有实现。

### 阶段 3：产品证据

- 执行契约测试、S1 黄金验收子集、异常 / 恢复 / 并发场景和跨契约矩阵。
- 由不负责实现的评测者复核证据；保留版本、输入、状态前后、决策轨迹、事件和结论。
- 进行受控用户验证，重点评估意图是否被满足、用户是否能理解并控制体验、体验是否较普通线性问答产生可感知价值。
- 用户验证用于检验产品假设，不以在线时长或模型平均分取代用户主导权与状态硬门槛。

### 阶段 4：继续 / 修订 / 停止

只有硬门槛通过、独立评测通过，且用户验证显示体验假设有支持时，才进入下一切片。失败时优先修正范围、交互或契约，不自动扩大功能。

## 6. AI 辅助编码执行协议

- 每个实现任务必须引用冻结契约、具体验收条件、受影响组件和禁止行为。
- 实现代理不能自行修改契约、黄金验收期望、严重级别或通过语义来让测试通过。
- 遇到歧义、冲突或缺少产品决策时，登记并暂停受影响部分，不得用“模型看起来合理”代替批准。
- 单元测试、集成测试、跨契约场景、故障注入和独立评测分别报告；测试绿灯不等于产品通过。
- 每个 PASS 必须有可复现版本、执行记录和证据位置；P0 违规直接阻断。
