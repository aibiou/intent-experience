## 二、产品方向（锁定，不再反复摇摆）

### 2.1 战略愿景

AI 时代，下一代大众体验产品可能从预先生产、分发内容，转向围绕用户当前意图动态组织和生成体验。

### 2.2 产品定义

一个能够理解用户当下的意图，实时组织适合的体验，并允许用户自然地探索、理解、模拟、创造、改变方向或结束的个人体验引擎。

### 2.3 核心产品假设

需要验证的不是 AI 能否回答问题，而是：

> **当系统能够理解用户当前的意图，并围绕这个意图动态组织一段连续体验时，用户是否会感到自己被理解、获得新的发现，并愿意自主地深入、改变方向、创造或结束？**

关键区别：

- 普通对话产品的基本交付物是**回答**
- 本产品需要交付的是**一段围绕用户意图组织起来的体验**
- 一次体验可以包含多个回答，但不能仅仅由多个回答拼接而成

例如：用户提出一个关于人类决策的问题 → 系统先提供一个有价值的解释 → 再根据用户的兴趣深入机制、比较不同观点、进行假设推演 → 甚至把其中的想法发展成一个可修改的创作成果。这些过程应当共享上下文，并由用户决定下一步走向哪里，而不是每轮都重新开始。

当然，不是每个问题都需要经历所有阶段。用户如果只需要一个答案，直接回答就是正确的产品行为。

### 2.4 产品成功标准

1. 用户能低摩擦地进入适合当下意图的体验
2. AI 能够理解用户真正想做什么，而不只是识别关键词
3. 体验具有内容质量、上下文连续性和探索价值
4. 用户始终能够纠正、深入、改变方向或停止
5. 用户可以自然地从理解进入模拟或创造，而不必重新描述已有上下文
6. 用户在体验结束时获得实际价值，而不是被系统强行留住

这些目标构成产品的长期方向。首个完整产品切片负责验证其中最重要的机制，而不是替代整个愿景。

## 三、必须停止的做法

以下行为模式在后续迭代中**明确禁止**：

1. **工程测试全部通过，却没有证明用户体验有价值**——测试绿是必要条件不是充分条件；每次迭代必须包含真实模型下的体验验证
2. **模型网关支持很多提供商，却没有验证真实模型能否驱动完整体验**——接入数量不是目标，驱动完整体验的质量才是
3. **状态机和策略设计得很严密，用户实际使用起来却像在填写表单或与普通聊天机器人对话**——工程严密性是底线，不是产品力；产品力由用户体验判定
4. **每次发现问题就增加一份规范，却没有持续交付可运行的产品**——治理文档不再扩张；问题修在代码里，证据留在运行中
5. **为了让当前版本容易完成，随意缩小产品目标，最后只剩一个简单的 AI 工具**——不缩减核心体验；体验的完整性优先于实现的便利性

## 四、工作原则：三件事同时守住

### 4.1 愿景不跑偏

- 每次迭代开始前问：这次改动让用户体验更接近「一段围绕意图组织起来的体验」了吗？
- 每次迭代结束后问：用户离「被理解、获得发现、愿意自主深入」更近了吗？
- 如果一个改动只提升工程指标而不影响用户体验，它的优先级低于直接影响体验的改动

### 4.2 工程不失控

- 运行时单写入、状态机合法转换、LLM 输出即提案、STOP/CHANGE 优先——这些不变量不因任何迭代放松
- vitest 秒级回归 + G3 黄金套件是安全网，每次迭代必须保绿
- P0 用户主导权、状态完整性、策略边界违反直接阻断——不存在「先上线后修」
- 新增代码必须有对应测试覆盖

### 4.3 产品持续变好

- 每次迭代必须产出可运行、可体验的产品（不是文档、不是规划、不是规范）
- 每次迭代必须用真实模型走完至少一条完整体验路径
- 发现的问题即时修复、即时验证、即时记录证据
- 用户的真实反馈（哪怕是产品负责人自己代测）优先级高于任何预先规划

## 五、迭代节奏

### 5.1 迭代单元

每次迭代 = 一个可运行的产品改动 + 真实模型验证 + 证据记录

不产出可运行产品的迭代不存在。只写文档不改动代码的迭代不存在。

### 5.2 迭代验证清单（每次迭代必须完成）

- [ ] `vitest run` 全绿
- [ ] `typecheck:core` 退出码 0
- [ ] `next build` 退出码 0
- [ ] 真实模型下走完至少一条完整体验路径（不是单元测试，是真实交互）
- [ ] 发现的问题已修复或已登记为已知残余
- [ ] 治理登记更新（decision-register CR 号 + readiness-record 版本）

### 5.3 优先级排序原则

1. **真实使用中暴露的体验缺陷**（最高优先——用户直接感知的痛）
2. **完整体验路径上的断点或退化**（影响体验连贯性的工程问题）
3. **提升体验质量的新能力**（让体验更好的产品改动）
4. **回归测试补全**（把代测教训固化为自动化测试）
5. **工程优化**（性能、可维护性等——不影响当前体验的不急）

## 七、本阶段行动线

### 行动线 A：持续修复真实使用中暴露的体验缺陷

- 产品负责人继续代测，发现即修复
- 每个修复必须有 vitest 回归覆盖
- 残余项跟踪到消除或确认可接受

### 行动线 B：真实模型下的核心体验闭环验证

不是代测单个功能点，而是从首页到作品墙走完 5 条完整体验路径：

1. 深海发光生物（discover 类——探索型体验）
2. 猫的呼噜声（discover → creation——从理解到创作）
3. 冥想放松（relax 类——意境型体验）
4. 自由输入探索（wild 类——无预设路径）
5. 续作链路（作品墙 → 新体验 → 新作品——回看与再创作闭环）

每条路径记录：体验是否流畅？模型回应质量？状态切换正确性？生成内容可靠性？用户控制感充分性？

### 行动线 C：产品力提升

基于行动线 B 的验证结果，识别并实施最能提升产品体验的改动。可能的方向（由验证结果驱动，不预先锁定）：

- 体验阶段的上下文连续性增强（减少「重新开始」感）
- 模型回应的体验化引导（让回应更像「体验的一部分」而非「问答」）
- 创作与探索的自然过渡（降低从理解到创造的门槛）
- 首页推荐与续讲的个性化（让回来更容易）

### 行动线 D：引入真实用户反馈

找 2–3 个非技术用户，观察他们使用产品的第一个 5 分钟。记录：
- 他们理解这是什么吗？
- 入口屏是否制造了好奇？
- 他们能自然地改变方向吗？
- 生成的内容让他们惊喜还是困惑？
- 他们在哪里卡住了？

用这些反馈决定下一步优化什么。

- 每次迭代的证据留在运行产物和代码中，不额外扩张文档体系

## 九、最终目标

> **让用户真正感受到：他们不必先学会使用复杂的工具，只需表达自己此刻想探索什么，系统就能帮助他们进入一段有价值、能深入、可创造、随时可以改变方向的体验。**

这是持续投入研发的最终理由。

工程底座是手段，模型接入是手段，评测体系是手段——用户感受到有价值的体验，才是目的。
